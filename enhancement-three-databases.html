Grazioso Salvare Dashboard — Aggregation Pipelines, Indexing & Access Control

Originally built in CS 340, Client/Server Development. Enhanced for CS 499.

Python MongoDB PyMongo Dash Jupyter

Artifact Description

The Grazioso Salvare animal shelter dashboard has two parts: a Python data access module, CRUD_Python_Module_Module5.py, which defines an AnimalShelter class wrapping PyMongo with create, read, update, and delete operations against a MongoDB collection of Austin Animal Center outcome records; and a Jupyter notebook, ProjectTwoDashboard.ipynb, that builds an interactive Dash web application on top of that class — a filterable data table, three rescue-type filter buttons (water, mountain/wilderness, disaster/individual tracking), a breed distribution pie chart, and a geolocation map. The client, Grazioso Salvare, is a fictional search-and-rescue organization that needed to identify shelter animals suited for rescue training based on breed, sex, and age.

Why This Artifact

Of the three courses considered for the databases category, this is the one where the database is not incidental to the application — it is the application. The AnimalShelter class is the only layer that talks to data, and every widget in the dashboard depends on how well that layer is designed, making it a direct test of database skills rather than a smaller supporting piece.

What Changed

Aggregation over pandas-side filtering. The original class only exposed find(), so every rescue-type button pulled the entire collection into memory and re-scanned it three times with duplicated filter logic. get_rescue_candidates() now runs a single aggregation pipeline keyed off a shared RESCUE_CRITERIA dictionary, and get_breed_counts() performs the group-and-count work for the pie chart as a MongoDB $group stage instead of a pandas value_counts() call.

Indexing. A compound index ordered by the equality-before-range rule (animal type and sex before breed and age), single-field indexes on breed and outcome type, and a 2dsphere geospatial index — which required a migration step, _migrate_geojson_location(), to backfill a proper GeoJSON field from the existing latitude/longitude columns. explain_read() and explain_aggregate() helpers let index usage be verified rather than assumed.

NoSQL-injection defense. A new aggregate() method validates every pipeline through _reject_dangerous_operators(), which blocks operators such as $where and $out from ever reaching the database.

Credential hygiene. Removed a hardcoded database password from source in favor of MONGO_USER/MONGO_PASS environment variables, created a least-privilege aacuser account (readWrite on the aac database only), and enabled server-side authorization — which had not been enabled at all previously, meaning the original hardcoded password was not being enforced by anything.

Course Outcomes Demonstrated

3

Designing and evaluating a computing solution while managing trade-offs — demonstrated by the compound index ordering itself: applying the equality-sort-range rule to put animal_type and sex_upon_outcome ahead of breed and moving the ranged age field to the end.

4

Using well-founded tools and techniques to deliver value — demonstrated by the aggregation pipelines and indexes replacing pandas-side scans, with explain_read()/explain_aggregate() providing a way to measure the improvement instead of assuming it.

5

Developing a security mindset — demonstrated by the sanitize-before-query pattern in _reject_dangerous_operators(), and by replacing an unenforced hardcoded credential with a least-privilege account and server-side authorization.
