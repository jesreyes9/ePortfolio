Contact Service — Secondary Index, Trie, and Merge Sort

Originally built in CS 320, Software Test, Automation, and QA. Enhanced for CS 499.

Java JUnit 5 Data Structures

Artifact Description

The Contact Service is a Java application consisting of a Contact class (contact ID, first name, last name, phone number, and address, each with input validation enforced in the constructor and setters) and a ContactService class that manages a collection of contacts. The original version stored contacts in a single HashMap keyed by contact ID, giving constant-time add, delete, update, and lookup, and it was backed by a JUnit test suite reaching roughly 95% coverage.

Why This Artifact

The original artifact had an honest, well-defined limitation: the HashMap gave O(1) lookup by contact ID, but no way to search or sort by name without an O(n) linear scan. That gap made it a genuine candidate for a data structures enhancement rather than a superficial one, and the existing strong test suite meant I could extend it with confidence that I wasn't building on top of hidden defects.

What Changed

Secondary hash index. A Map from lowercased last name to a Set of contact IDs, trading a small amount of memory for O(1) average-time exact-match lookup by last name instead of a linear scan.

Trie for prefix search. A new TrieNode class, with children keyed by character and a set of contact IDs stored at each terminal node, supporting prefix search and autocomplete in O(k) time, where k is the length of the search prefix — independent of how many contacts exist.

Hand-written merge sort. Implemented directly rather than delegated to a library sort call, giving a guaranteed O(n log n) divide-and-conquer sort with a composed comparator that orders contacts by last name, then first name.

The add, delete, update-first-name, and update-last-name operations were all rewritten to keep the primary map, the secondary index, and the trie synchronized on every mutation, and the JUnit suite gained 26 new tests covering the added behavior.

Course Outcomes Demonstrated

3

Designing and evaluating a computing solution using algorithmic principles while managing design trade-offs — demonstrated by selecting and justifying three distinct structures for three distinct access patterns, trading extra memory for lookups that used to cost O(n) and now cost O(1) or O(k).

4

Using well-founded techniques, skills, and tools to deliver value — demonstrated by implementing the trie traversal and merge sort from first principles, and extending the existing JUnit suite so the new algorithms are verified with the same rigor as the original artifact.
