Travlr Getaways — Secured Booking Module & Role-Based Access Control

Originally built in CS 465, Full Stack Development I. Enhanced for CS 499.

MongoDB Express Angular 17 Node.js JWT

Artifact Description

Travlr Getaways is a full-stack MEAN application that serves two audiences from a single Node/Express backend: a public marketing and booking site rendered with Express and Handlebars, and an Angular 17 single-page application that travel agents use to manage the trip catalog. The original artifact included a Trip model, a REST API for listing, adding, and updating trips, and JWT-based authentication that protected the write endpoints.

Why This Artifact

Travlr Getaways is the largest and most architecturally complete project in my coursework, giving room to demonstrate skills across the full stack rather than in a single file. The enhancement completes a secured Booking feature module with role-based access control (RBAC), implemented across the model, API, security layer, and Angular client.

What Changed

Booking feature. A new Mongoose Booking model (trip code, trip name, customer name/email, seat count, status) and a bookings controller with full create, read, and cancel operations. Booking creation validates that the trip exists, that it hasn't already started, and that the requested seats don't exceed the trip's remaining capacity — computed with a MongoDB aggregation pipeline rather than a live counter that could drift out of sync. The Trip model gained a maxTravelers field to support the capacity check.

Role-based access control. The User model gained a role field (admin or agent), embedded in the JWT payload at sign-in. Authentication moved out of the routes file into a dedicated app_api/middleware/auth.js containing authenticateJWT and a new authorizeRoles(...roles) middleware that gates an endpoint to specific roles. Self-registration always assigns the agent role server-side, so a client can never grant itself admin privileges.

A real bug, fixed. While extracting authenticateJWT, I found that the original code called jwt.verify() with an asynchronous callback but invoked next() immediately afterward instead of from inside that callback — meaning a request could reach a protected controller before token verification had actually completed. The rewritten middleware only calls next() from inside the verification callback on success.

Angular client. A Booking model, a BookingDataService, a booking-list component with a role-gated cancel action, and an add-booking reactive form component, wired into the existing routing and navigation. The AuthenticationService gained a canManageBookings() helper that reads the role out of the decoded JWT so the SPA's UI gating mirrors what the API enforces.

Course Outcomes Demonstrated

3

Designing and evaluating a computing solution while managing trade-offs — demonstrated by adding a maxTravelers field and an aggregation-based capacity check instead of ignoring capacity or scanning the full collection on every booking.

4

Using well-founded techniques and tools to deliver value — demonstrated by the Booking module spanning the model, API, and Angular client as a self-contained, RESTful feature.

5

Developing a security mindset — demonstrated most directly by the RBAC middleware, the server-side role default on registration, and the authenticateJWT fix, which closes a genuine adversarial-exploit path.
